In short.

Adal is an auction service where bidding stays correct when many people bid at once: one winner and one price, every time.

The problem

Most auction platforms offer one or two ways to sell, and rarely explain how they stay correct when bids arrive in the same instant. A buyer has to trust the price and the clock without seeing either work.

Our answer

A seller picks the format per listing: English, Dutch, sealed first-price or sealed second-price (Vickrey). All four run on one engine. The server clock is the only authority, and the database decides who won by locking.

The fall MVP

Accounts with email verification and a second factor, listings with browse and search, English auctions with sniping protection and live updates, automatic closing, one transaction per sale finalized with a fresh code, an audit log, concurrency tests and a usability test.

What the MVP shows.

The demo is one story told in order: a seller lists an item, two buyers compete for it, the clock closes it, and the winner pays. Each step is something the system must do correctly, not only look right.

  1. Register and secure the accountEmail verification, then a TOTP second factor. It is mandatory for sellers and admins.
  2. List an itemThe seller chooses a format, sets start, end and a reserve that bidders never see.
  3. Find itBrowse and search. Every card shows a word status and a written closing time.
  4. Bid from two browsersThe price moves on both screens within a second. The beaten bidder is told "Outbid" in words.
  5. Watch the closeA late bid extends the closing time (sniping protection). The auction then closes by itself.
  6. Pay with a fresh codeThe winner finalizes the purchase with a new MFA code. One sale makes exactly one transaction, and the audit log records it.

One engine, four strategies

English, Dutch, sealed first-price and Vickrey share one state machine and one place that validates a bid. Each format is a module that only decides what a valid bid is and who wins. Adding a format in spring does not touch the locking.

PostgreSQL row locking

Two simultaneous bids cannot both read the same price and both win. The second waits for the first to commit, then is checked against the new price. The same mechanism makes sure a sale creates exactly one transaction.

Server clock

Browsers show a countdown, but only the server's time decides whether a bid arrived in time. Nothing a client sends can move a deadline.

Channels for live updates

Watchers hold a WebSocket and receive each accepted bid, so nobody refreshes. The target is that 95% of watchers see a new bid within 1 second.

React and Django REST

A clear contract between screens and rules. Interface contracts let the front end build against mocked responses while the backend is still being written.

Security

TOTP at login, and a second, fresh code to finalize a purchase. Controls follow the OWASP Top Ten (2021) items A01, A02, A03, A05, A07 and A09. Audit log entries cannot be edited through the application.

Docker

One command starts the whole stack, so a teammate or an instructor can run the demo without setup.

What happens to one bid

  1. The bid arrivesThe browser sends the amount over REST. The client's clock plays no part.
  2. The auction row is lockedAny other bid on the same auction waits its turn.
  3. Three checksThe auction is active, the server time is before the close, and the amount beats the current price by the minimum increment ({{T}}: fixed or a percentage).
  4. Write and extendThe bid and the new price are stored. A bid near the end extends the close (sniping protection, length {{T}}).
  5. Commit and releaseThe lock is freed. The next waiting bid is checked against the new price.
  6. BroadcastChannels sends the new price, time and status to every watcher.

How we score usability and design

Each system gets 1 to 5 on the same five questions, on the same pages: can a first-time bidder place a bid without help; is the closing time written out; is the result of a bid shown where the bid was made; is state conveyed by words as well as color; is the page readable on a phone.

Where we are stronger

Variety of formats on one engine, a correctness story we can test and show, and a second factor at the point of purchase.

Where we are not

Scale, reputation and fraud scoring, real payments and identity checks (KYC) are out of scope. We say so plainly in the report.

Brand language.

Adal means fair and honest. In an auction, fairness is balance: the same rules, the same clock, the same weight for every bid.

Rules we keep

The closing time is always written out beside a countdown. One primary action per view. Status is never color alone. No exclamation marks, no hype words.

The boards

A seven-board brandbook covers the cover, mark, color and type, components, a website home page and auction page, and three app screens. Every screen in the demo is built from it.

How we run the project.

Method

Requirements first, then short weekly iterations on one board. The MVP ships in fall; the rest of the formats follow in spring. Concurrency tests start in week 10 beside the locking work, so correctness is checked while it is being built, not at the end.

Name we use for this: {{T}}, for example Agile with weekly sprints.

Tools

A GitHub Projects board where every task has one owner, one reviewer, a due week and the requirement IDs it covers. Git feature branches and pull requests, with at least one reviewer per merge. A Gantt chart and a PERT network, updated at the weekly sync.
